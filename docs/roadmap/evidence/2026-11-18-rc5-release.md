# MehrChain RC5 release handoff — 2026-11-18

Candidate: `1.0.0-rc.5`, Android `versionCode=5`, application ID
`com.mehrchain.app`. The latest published GitHub release at inspection was
`v1.0.0-rc3`. RC5 remains a local candidate; no tag, public APK, deployment,
or production schema change was made in this handoff.

## Verified locally

- Production Nx frontend/backend build passed with cache disabled. The existing
  CommonJS QR warning remained. Nx passed 298 frontend and 174 backend tests;
  17 release/roadmap script tests and the startup stylesheet guard passed.
  The public GitHub release-history preflight accepted the unused RC5 tag and
  increasing code; this is not a signing-environment check.
- Chrome controlled by a real Angular service worker loaded the RC4 build,
  detected RC5 on the same localhost origin, refused a cancelled Reload,
  then loaded the new hashed JS bundle on confirmed Reload. A separate
  synthetic next manifest showed that opening and dismissing the RC5 notice
  did not move the page or create horizontal overflow at 320 CSS px.
- Profile Colors was exercised with a synthetic unlocked account at 320, 390 and
  544 CSS px in light/dark. Create opens the draft, swatch updates name and
  preview, a partial hex disables saving, and Cancel leaves the old named color.
  Angular tests cover the lock, draft boundaries and error/persistence behavior.
  Visual checks do not substitute for Android software keyboard testing.
- Android update tests cover the signed release policy, same certificate and
  app ID, increasing versionCode, rejected prereleases and untrusted download
  URLs. No same-key device upgrade or live update feed is claimed.

## Database gate — before pushing main

The cached Render/production connection references agree on target identity.
Read-only inspection of that database found seven release migrations recorded,
through `20261020000000_mero_color_collection`, with no unresolved failed
entries. `20261021000000_optional_usernames` and
`20261118180000_chain_heart_completion` were not recorded. The username column
was still non-null, `usernameSource` and the heart `completionId` were absent,
and the case-insensitive username collision count was zero at inspection.
The currently serving Render binding/revision and a fresh restorable recovery
point could not be verified: the Neon console returned a region block, Pages
HTTP checks did not connect and Render's version read timed out. The database
evidence is actionable but does not establish the cause of a live username write.

1. In the authorized Render and Neon consoles, privately match the live service's
   database target. Confirm whether pushes to main deploy automatically. Create
   a pre-change recovery branch/snapshot and a disposable populated child; keep
   recovery references and credentials private.
2. On the disposable child, set the direct URL in `DATABASE_URL` without printing
   it. Run `node scripts/release-migrate.cjs status`. Confirm exactly the expected
   two migrations and no unexpected failure or drift. Run
   `node scripts/release-migrate.cjs deploy` and then `status`. Verify that
   existing account IDs, usernames, and daily heart allowances are preserved,
   nullable usernames and event-linked hearts work, and a repeat deploy is a
   no-op. See the [database procedure](../../database_migration_procedure.md).
3. Verify the target/recovery point again. Apply the reviewed release-chain
   migrations to the confirmed production database, check the migration status
   and schema, then run `git push origin main`. Do not run the historical
   `prisma/migrations` directory, `migrate reset`, or a schema push.
4. Confirm the direct and Pages `/api/version` responses and the deployed web
   revision. Stop publication on mismatch, pending migration, failing startup,
   or unexpected account/Chain behavior. For rollback favor the previous
   compatible application build and leave additive schema/data intact.

## Build, test, and publish the APK

1. A regular main push builds only the test/debug artifact. After the database
   and deploy gates pass, open [Build & Release Android APK](https://github.com/farzad-bahadorifar/mehrchain/actions/workflows/build-apk.yml).
   On **Run workflow**, choose **main**, set `version_tag=v1.0.0-rc.5`,
   select `sign_candidate`, and leave `publish_release` off. Approve the
   `android-release` environment if prompted. Verify that the workflow SHA is
   the intended main commit. Signing uses the existing key and pinned fingerprint;
   never use the debug APK to test a same-key upgrade.
2. From the successful run, download **mehrchain-signed-candidate-v1.0.0-rc.5**.
   Extract the ZIP and verify `Get-FileHash .\mehrchain-release.apk -Algorithm SHA256`
   against `SHA256SUMS` and `release-manifest.json`. Check manifest version,
   versionCode, app ID and certificate against trusted records.
3. Upgrade a prior same-key installation on a test Android phone without
   uninstalling or clearing storage. Use the package installer or
   `adb install -r mehrchain-release.apk` from an authorized test PC. If
   Android reports a signature conflict, stop; do not uninstall to force a pass.
   Record installed version, device/OS, startup, session and retained data, then
   use the manual checklist below.
4. After acceptance, tag the exact workflow SHA, not an unverified new HEAD:
   `git tag -a v1.0.0-rc.5 <accepted-sha> -m "MehrChain 1.0.0-rc.5"`.
   Run `git push origin refs/tags/v1.0.0-rc.5`. The tag, not the local version
   edit, triggers signed publishing. Never replace or force-push a released tag.
   On [GitHub Releases](https://github.com/farzad-bahadorifar/mehrchain/releases),
   verify the prerelease contains the signed APK, manifest and checksum.
5. Timing: recent main builds took roughly 2.5–5.2 minutes. Allow about
   5–15 minutes from start of a signed run for both jobs, plus any runner queue
   or environment approval. Follow job state in Actions rather than waiting a
   fixed interval. If it pauses at the environment gate, a maintainer must act;
   if it fails, inspect the failing job and do not publish alternate unsigned assets.

## Manual acceptance checklist

Use a disposable authorized account and installation. Record app build/SHA,
date, phone model, Android/Chrome versions, display mode, theme, and pass/fail.
Do not capture tokens, emails, raw invite codes, passwords or private Why text.

| Check | Expected |
| --- | --- |
| APK upgrade and startup | Upgrade in place; Profile shows RC5; session, habits, and earned colors are retained. No blank startup or stray Mero glow after background and return. |
| Profile / T30 | Chrome tab and installed PWA, light and dark: open Profile, Account, Badges, Colors and Appearance directly; return from each. Open the username and color-name keyboard: input retained and Cancel/Save reachable without sideways scrolling. |
| Mero Colors | Fresh account cannot edit or save. An account with an earned slot can preview a swatch, cancel without applying, save a named color, reload, and see it retained. Switching app theme does not rewrite earned colors. |
| PWA cold start / T56 | Note serving revision and controlling worker. Capture five disposable fresh-install launches and five existing-install process restarts; no oversized mascot, unstyled controls or persistent blank screen. Keep frames of any failure. |
| Web update | Keep a controlled older PWA tab open before a newer deployment. Use Appearance / Check for updates. Later neither reloads nor moves the form. Cancel the Reload prompt to retain the old build, then confirm it and verify the new version and persisted data. |
| Android updater | RC5 is an intentional prerelease: it must **not** be advertised by the stable-only in-app APK feed. Test RC5 by signed manual upgrade; verify discovery on a later accepted stable, same-key, higher-code release. Do not remove the prerelease filter to force the test. |
| Username / T29 | Verify reachable direct/proxy revisions; on the authorized account save an available username, reload, then remove deliberately. Record HTTP status/class and confirmed UI result. An API timeout is not a username root cause. |
| Chain | With two test accounts, an incomplete link is managed in Connect only. Complete the linked step and see Show Up update; send one heart and verify confirmed fill and anonymous received support. Details and private disconnect stay in Connect. |
| Access | Verify the sign-in method being announced for the pilot. Do not advertise public OTP/reset without an independently verified sender/domain and real delivery. |
